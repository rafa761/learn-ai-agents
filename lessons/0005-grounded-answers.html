Grounded answers

Yesterday you built a retriever that ranks the right chunk first. Today the loop closes: the chunks ride into the prompt, a model answers from them and only them, every claim carries a [Doc N] you can check — and when the answer isn't in the corpus, the system says so. That last behaviour is not a failure mode. It is the entire point.

Today's win

One file, rag-qa.ts: retrieval from lesson 0004, a zod-checked seam from lesson 0003, a live Claude call from the SDK — and a two-question run where the on-corpus question comes back citing the book and the off-corpus question comes back refusing honestly. Full RAG, end to end, on your machine.

§1Why generation is the dangerous half

Here is the uncomfortable fact about the model at the end of your pipeline: it does not need your retrieved chunks to answer. Ask it about chunk overlap and it will happily produce a fluent paragraph from its training weights — stale at best, invented at worst. The retrieval layer you built solves finding the right text; nothing about it forces the model to use that text and nothing else. Grounding is the discipline that closes that gap, and it lives almost entirely in the prompt (book §16.2.4).

This is also where your last quiz miss pays off. You distinguished (or now can) three limits: the embedding window shapes each chunk; the generator's input budget caps how many chunks fit in the prompt; the generator's output limit caps the answer's length and has nothing to do with chunks. Today the middle one becomes code: you choose k, you send k chunks, the prompt pays for them.

§2Three ideas, each with a why

1. The ONLY-context instruction. The system prompt tells the model: answer using only the provided context documents, and say so explicitly when they don't contain enough. Why both halves? The first blocks the model's default behaviour (answering from weights — its training makes this its reflex, not its fault). The second redefines refusal as a correct answer: “the context does not contain this” is exactly what a trustworthy system says when it's true. Without that clause, the model faces a false choice between ignoring you and inventing.

2. The [Doc N] citation. Each retrieved chunk enters the prompt numbered — [Doc 1] (score 0.541) …text… — and the model must mark claims with the Doc it used. Why: it converts a fluent answer into an auditable one. You can check any sentence against chunk 1 in seconds. In production this is the difference between “the AI said” and “the manual says”.

3. Top-k, never a score threshold. You keep the best k=3 chunks — you do not keep “everything scoring above 0.4”. Why, in plain terms: a cosine score is not a property of a text. It's a property of a pair — this query against this chunk, measured by this model. Your two live queries from lesson 0004 scored 0.54 for a great match and 0.17 for no match; a broader query can max out at 0.35 and a narrow one never dip below 0.5. There is no universal line where a score becomes “relevant” — a hardcoded threshold is a bug that happens to work on the queries you tested. The ranking is the dependable part. So: take the best k, and let the say-so-if-insufficient instruction decide whether what came back is enough. The generator is your threshold — and it's a better one, because it reads the text, not the number.

// The G arrives. Retrieval (lesson 0004) meets generation (lessons 0002–0003):
// chunks -> zod-checked seam -> grounded prompt with [Doc N] citations -> Claude.
// This file IS the capstone in miniature — at four paragraphs instead of 636 pages,
// the only difference between here and there is scale.
// Live: needs ANTHROPIC_API_KEY. Two haiku-class calls, pennies.

import Anthropic from "@anthropic-ai/sdk";
import { pipeline } from "@huggingface/transformers";
import { z } from "zod";

process.loadEnvFile(".env"); // must run before the client reads the env
const client = new Anthropic(); // reads ANTHROPIC_API_KEY itself

// ---------- retrieval layer: lesson 0004, third typing — retrieval is remembering ----------

const EXCERPT = [
  "Retrieval-Augmented Generation equips large language models with a dynamic, updatable external memory, enabling accurate, grounded, and verifiable responses across knowledge-intensive tasks.",
  "Large language models store knowledge parametrically, compressed into billions of weights during training. This creates three fundamental limitations: hallucination, where models confidently generate plausible but incorrect statements beyond their reliable knowledge boundary; knowledge staleness, because training data has a cutoff date; and domain specificity, since general-purpose models lack deep knowledge of proprietary codebases and documents.",
  "Chunking is the process of splitting documents into segments that are small enough to fit in an embedding model's context window, semantically coherent, and containing enough context to be useful when retrieved in isolation.",
  "The simplest strategy splits every W tokens with an overlap of O tokens between consecutive chunks. Overlap preserves context across boundaries: a sentence cut at a chunk edge still appears whole inside its neighbour chunk, so retrieval never loses a thought merely because a window ended mid-thought.",
].join("\n\n");

function chunkTexts(text: string, size: number, overlap: number): string[] {
  if (overlap >= size) throw new Error(`overlap (${overlap}) must be smaller than size (${size})`);
  const words = text.split(/\s+/).filter(Boolean);
  const step = size - overlap;
  const out: string[] = [];
  for (let start = 0; start < words.length; start += step) {
    const window = words.slice(start, start + size);
    if (window.length === 0) break;
    out.push(window.join(" "));
    if (start + size >= words.length) break;
  }
  return out;
}

function cosine(a: ArrayLike<number>, b: ArrayLike<number>): number {
  let dot = 0;
  let normA = 0;
  let normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}

const embedder = await pipeline("feature-extraction", "Xenova/all-MiniLM-L6-v2");

async function embed(text: string): Promise<Float32Array> {
  const tensor = await embedder(text, { pooling: "mean", normalize: true });
  return tensor.data as Float32Array;
}

const chunks = chunkTexts(EXCERPT, 60, 12);
const chunkVectors = await Promise.all(chunks.map(embed));

// top-k, not top-threshold: cosine scores have no absolute meaning across queries or
// models — only the RANKING is dependable, so "best 3" is a knob, "score > 0.4" is a bug.
const TOP_K = 3;

async function retrieve(query: string): Promise<{ text: string; score: number; index: number }[]> {
  const queryVector = await embed(query);
  return chunks
    .map((text, index) => ({ text, score: cosine(queryVector, chunkVectors[index]), index }))
    .sort((x, y) => y.score - x.score)
    .slice(0, TOP_K);
}

// ---------- the seam: retrieval output becomes prompt input (zod, lesson 0003's doctrine) ----------

const RetrievedChunk = z.object({
  text: z.string(),
  score: z.number(),
  index: z.number(),
});
type Retrieved = z.infer<typeof RetrievedChunk>;

function asRetrieved(raw: unknown): Retrieved[] {
  // safeParse at the seam, exactly like lesson 0003's parseReply: the prompt builder
  // downstream depends on this shape — the schema is the contract, checked.
  const parsed = z.array(RetrievedChunk).safeParse(raw);
  if (!parsed.success) throw new Error(`retriever output failed its own schema: ${parsed.error.message}`);
  return parsed.data;
}

// ---------- the grounded prompt: book §16.2.4, translated ----------

function buildGroundedPrompt(query: string, docs: Retrieved[]) {
  const context = docs
    .map((d, i) => `[Doc ${i + 1}] (score ${d.score.toFixed(3)})\n${d.text}`)
    .join("\n\n");
  return {
    system:
      "You are a retrieval-augmented assistant. Answer the question using ONLY the " +
      "provided context documents. If the context does not contain enough information, " +
      "say so explicitly — do not use your own knowledge to fill gaps. Cite your sources " +
      "using [Doc N] notation.",
    user: `Context documents:\n\n${context}\n\nQuestion: ${query}`,
  };
}

// ---------- the loop, closed: ask, retrieve, ground, generate ----------

const QUESTIONS = [
  "why must consecutive chunks share overlapping words", // on-corpus: expect [Doc N] citations
  "what do Vogons think of poetry", // off-corpus: expect an honest "not in the context"
];

for (const question of QUESTIONS) {
  const docs = asRetrieved(await retrieve(question)); // the seam, checked
  const prompt = buildGroundedPrompt(question, docs);

  const reply = await client.messages.create({
    model: "claude-haiku-4-5",
    max_tokens: 512,
    system: prompt.system,
    messages: [{ role: "user", content: prompt.user }],
  });

  const answer = reply.content
    .filter((b): b is Anthropic.TextBlock => b.type === "text")
    .map((b) => b.text)
    .join("");

  console.log(`\n${"=".repeat(72)}\nQ: ${question}`);
  console.log(`fed the model ${docs.length} chunks: ${docs.map((d, i) => `[Doc ${i + 1}] ${(d.score).toFixed(3)}`).join("  ")}`);
  console.log(`-${"".padEnd(70, "-")}`);
  console.log(answer.trim());
}

§4What you just built

The complete online half of RAG, and therefore — with lesson 0004 — the complete pipeline: chunk → embed → retrieve → check → ground → generate, every arrow typed by you, one honest cast, one schema at the one seam where subsystems meet. Two observations to carry forward:

Determinism where it matters. Same corpus, same model, same cache → identical scores across sessions. Your retrieval layer is a pure function of its inputs; only the generation step is stochastic. That split is why RAG systems are debuggable: when an answer is wrong, you first ask did retrieval hand over the right chunks (deterministic, checkable — you just did) before suspecting the model.

The capstone is this file, scaled. Four paragraphs become 636 pages; in-memory cosine becomes a vector index (an optimization, not a redesign — the vectors and the ranking are unchanged); the EXCERPT constant becomes a loader; the two questions become your users'. The architecture you can hold in working memory today is the architecture you'll ship.
