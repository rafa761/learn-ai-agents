The tool-use round trip

Everything that crosses the wire in one Claude tool call — the shapes, the stop reasons, and the three laws of the ledger. Print me.

Built in Lesson 0002. Companion references: the Python → TypeScript phrasebook. Canonical source: Anthropic — Tool use with Claude.

§1The cycle

one lap of the loop
you ──── messages + tools ────▶ Claude
you ◀─── stop_reason: "tool_use"
         content: [ {type:"tool_use", id, name, input} ]        ← data, not execution
you      run name(input), build {type:"tool_result", tool_use_id, content}
you ──── assistant echo (verbatim) + user [tool_result] ────▶ Claude
you ◀─── stop_reason: "end_turn" | "tool_use" | …               ← repeat until done

The model never executes anything. A tool_use block is JSON naming a function and its arguments; validating and dispatching it is your program's job (docs). One response may carry several tool_use blocks — answer all of them in the same follow-up user message (parallel tool use).

§2The three laws of the ledger

  1. Append-only. The conversation is a ledger you grow, never edit — every hop appends.
  2. Echo verbatim. The assistant turn (its content array, including tool_use blocks) goes back into the next request unchanged.
  3. Every call answered. Each tool_use gets a tool_result (matching tool_use_id) in the immediately following user message. Break this and the API rejects the request — verified live: API 400: … Each tool_use block must have a corresponding tool_result block in the next message.

§3stop_reason — the loop's control signal

valuemeaningyour move
"tool_use"model stopped to call your tool(s)execute, append tool_result, call again
"end_turn"model finished its answerread the text blocks; loop exits
"max_tokens"output hit the max_tokens cap, mid-thoughtcontinue (ask it to go on) or raise the cap
"stop_sequence"output hit a stop sequence you setapplication-specific handling

Other values exist (e.g. refusals, server-tool pauses) — see handling stop reasons. In a hand-rolled loop, treat unknown values like "end_turn": stop, don't crash.

§4Wire shapes (minimal)

request — declare a tool (JSON Schema, not TypeScript)
{
  "model": "claude-sonnet-4-5",
  "max_tokens": 1024,
  "tools": [{
    "name": "lookup_guide_entry",
    "description": "Look up a Guide entry…",      // ← a prompt; the model reads it to decide
    "input_schema": { "type": "object", "properties": { … }, "required": […] }
  }],
  "messages": [ …the ledger… ]
}
response — a tool call arrives as data
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text", "text": "Let me check the Guide…" },
    { "type": "tool_use", "id": "toolu_01A…",
      "name": "lookup_guide_entry", "input": { "topic": "towel" } }
  ]
}
what you append next — two messages, then call again
{ "role": "assistant", "content": …echo response.content verbatim… }
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01A…", "content": "About the most massively useful thing…" }
] }

§5Errors are results, not exceptions

When a tool fails, don't throw past the loop — return the failure as the tool's result content (optionally "is_error": true) so the model can see it, self-correct, and try again. A thrown exception kills the whole run; an error result keeps the loop alive (handle tool calls). The unknown-tool default arm in your dispatch switch is exactly this: error: unknown tool "…".

§6Circuit breakers

Every production loop ships with a hop cap and a token budget — the canonical pseudocode in Roitman 2026 ch. 19 §19.4 (arXiv:2606.24937) takes max_steps as a parameter, and Anthropic's Building Effective Agents lists action limits among the guardrails that separate an agent from a while (true). A model stuck calling tools forever is a production incident with a meter running.
