zod at the trust boundary

The four moves that replace hand-written guards at any boundary the compiler cannot vouch for — model output above all. Print me.

Built in Lesson 0003. Companion references: the tool-use round-trip cheat sheet and the phrasebook. Canonical source: zod docs.

§1The four moves

define → parse → infer → dispatch
import { z } from "zod";

// 1. DEFINE — the schema is a value; the model's world, in code
const Args = z.object({ topic: z.string() });

// 2. PARSE — unknown in, proven value out (or a typed failure)
const r = Args.safeParse(block.input);          // block.input: unknown

// 3. INFER — the TYPE comes from the schema; one source of truth
type Args = z.infer<typeof Args>; // the type is DERIVED, never declared twice

// 4. DISPATCH — only proven values reach your functions
if (r.success) lookup(r.data.topic);              // r.data.topic: string

Interfaces describe; schemas enforce. A z.object is checked at runtime and stripped of unknown keys by default — the same runtime the model talks to. Declare the discriminated union (z.discriminatedUnion("type", [Text, ToolUse])) and narrowing works exactly as it did with hand-written interfaces.

§2parse vs safeParse — closed world vs open world

callon bad inputuse when
Schema.parse(x)throws ZodErrorthe shape is on you: your config, a schema you own — failure is a bug, crash loudly
Schema.safeParse(x)returns { success: false, error }the shape is on the world: model output, user input, third-party JSON — failure is data, route it

Model-adjacent boundaries are open world almost by definition. The envelope of an API you call can be closed-ish (parse, throw — your transport is broken); the content the model produced is open (safeParse, drop or report).

§3Errors are results

a rejected tool call becomes the model's next input
const r = Args.safeParse(block.input);
const content = r.success
  ? lookup(r.data.topic)
  : `error: invalid arguments\n${z.prettifyError(r.error)}`;  // human- AND model-readable
return { type: "tool_result", tool_use_id: block.id, content };

Not an exception — a result the model reads and retries against (Anthropic: handle tool calls — error signaling). Caveat observed live (2026-09-07): the model skims. If your enforced schema drifts from the declared input_schema, it may guess values rather than read the error — keep declaration and enforcement in sync.
